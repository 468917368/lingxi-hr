# Mock Interview 百宝箱工作流设计

> **面向对象：** 百宝箱平台侧的工作流配置（D 成员 lingxi-hr 对接）
> **通信方式：** 百宝箱 tboxsdk 生成型调用 `TboxClient.completion(appId, inputs, userId)`（SDK 文档 §3）
> **关联文档：** `模拟面试agent-coding-plan.md`（D 侧代码）、`后端总体系分文档.md` 5.5.9/5.6.2/5.6.4
> **核心结论：** Mock Interview 三个环节（出题/评分/报告）都是**单次无状态生成任务**，不使用对话型 Agent，创建 **3 个独立的生成型工作流**。

---

## 一、总体设计

### 1.1 三个工作流清单

| 工作流 | 平台应用名 | appId（平台已建立 2026-08-04） | 触发场景 | D 侧类 |
|--------|-----------|------------------|---------|--------|
| 出题工作流 | `lingxi-mock-generate` | `202608APE9vh20999665` | `POST /mock-interview/generate` | `MockInterviewAgent.generate` |
| 评分工作流 | `lingxi-mock-score` | `202608APlpZR21033809` | `POST /mock-interview/{sessionId}/answer` | `MockInterviewAgent.answer` |
| 报告工作流 | `lingxi-mock-report` | `202608AP7lse21015615` | `GET /mock-interview/{sessionId}/report` | `MockInterviewAgent.report` |

### 1.2 SDK 调用方式（D 侧统一封装）

> **路由确认（2026-08-04）**：正确路由为对话型接口 `POST https://api.tbox.cn/api/chat`（`Authorization: <raw token>`，无 Bearer 前缀）。SDK 0.0.10 的 `completion()` 走 `/api/completion` 路由**不存在**（ROUTE_NOT_FOUND），故统一改用 `chat()`；工作流参数通过 **query 文本**传入，工作流大模型节点从 query 中提取参数。

```java
TboxClient client = new TboxClient(new HttpClientConfig(token)); // 全局单例

// query = 自然语言指令 + 参数（由 MockPromptBuilder 组装，含 jobInfo/resumeInfo/questionCount 等）
String query = "请为候选人生成5道模拟面试题。\n\n【岗位考察要点】\n...\n\n【候选人简历画像】\n...";

Iterable<Map<String, Object>> chunks = client.chat(appId, query, userId);
// userId 传 candidateId.toString()；拼接 chunks 中 payload.text → 完整 JSON → 解析
```

> **约束**：D 侧不传结构化 `inputs`（`/api/chat` 仅支持 query 文本）。工作流各场景所需参数（出题 `jobInfo`/`resumeInfo`/`questionCount`；评分 `questionContent`/`questionType`/`referenceAnswer`/`candidateAnswer`；报告 `jobInfo`/`questions`/`overallScore`）全部拼入 query，工作流 System Prompt 需说明"从用户输入中提取以下字段"。

### 1.3 配置项（D 侧 application.yml）

```yaml
baibaoxiang:
  api:
    key: ${TBOX_API_KEY:your-tbox-api-key}   # 百宝箱访问令牌（共用，一个账号一个，已就绪 2026-08-04）
  agent:
    generate-app-id: ${TBOX_GENERATE_APP_ID:202608APE9vh20999665}   # 出题

    report-app-id: ${TBOX_REPORT_APP_ID:202608AP7lse21015615}       # 报告
```

## 二、工作流 1：出题工作流（lingxi-mock-generate）

> **职责**：基于【岗位考察要点】+【候选人简历能力画像】生成定制模拟面试题。

### 2.1 输入参数（拼入 query 文本，工作流 System Prompt 提取）

| 字段 | 类型 | 必填 | 说明 | 长度建议 |
|--------|------|:---:|------|---------|
| `jobInfo` | String | 是 | 岗位考察要点（jobType + coreSkills + interviewFocus + softSkills，由 D 侧文本化） | ≤ 1500 字 |
| `resumeInfo` | String | 否 | 简历能力画像（5 维分 + subDimensions 技能/年限 + 项目要点；无简历传空串） | ≤ 2000 字 |
| `questionCount` | Integer | 是 | 题目数量：5 / 8 / 10 | - |

**D 侧 jobInfo 拼装示例**（来自 B `/internal/jobs/{jobId}/requirements`）：
```
岗位类型：高级前端工程师
核心技能：React(精通,必选) / TypeScript(熟练,必选) / Node.js(了解)
考察重点：虚拟DOM原理、React性能优化、前端工程化、跨端方案
软能力：沟通协作(重要) / 结果导向
行业经验：5年以上Web应用开发经验
```

**D 侧 resumeInfo 拼装示例**（来自 C `/api/v1/resumes/{id}/ability-model` + 简历详情）：
```
专业技能:78 / 项目经验:82 / 行业认知:65 / 综合素质:70 / 学习成长:75
技能列表: React、Vue、Webpack、TypeScript
工作年限: 4年
项目要点: 主导过中后台低代码平台（模块化、性能优化）、参与移动端H5重构
```

### 2.2 工作流节点设计

```
[输入节点] 直接接收用户 query 文本（无需自定义参数变量）
      │
      ▼
[大模型节点] 绑定下方 System Prompt，从 query 文本中提取【岗位考察要点】【候选人简历画像】
      │
      ▼
[输出节点] 输出格式 = JSON（强烈建议开启平台"结构化输出/JSON模式"）
      │
      ▼
返回 { "questions": [...] }
```

### 2.3 System Prompt（平台大模型节点直接粘贴，v4 实测生效 2026-08-06）

> ⚠️ 变量两条铁律（平台实测）：
> 1. **不要引用工作流输入参数变量**（如 `{{jobInfo}}`、`{{resumeInfo}}`）——D 侧走 `/api/chat` 只传 query 文本，这些变量为空。
> 2. **必须引用开始节点的用户输入** `{{input_hgtoen-currentChatByUser-当前对话信息}}`——大模型节点想用开始节点的用户输入，必须在提示词中显式添加该变量，否则读不到 D 侧传来的 query。需要上下文时再追加 `{{input_hgtoen-historyChat-历史对话信息}}`。

```
你是一个资深的技术面试官，负责根据目标岗位和候选人简历生成模拟面试题。
用户消息{{input_hgtoen-currentChatByUser-当前对话信息}}中提供【岗位考察要点】和【候选人简历画像】，所有出题信息都从用户消息中提取，不要用外部知识替代。

一、硬性约束
1. 严格输出用户消息指定的题目数量 N 道（N 从"请为候选人生成N道模拟面试题"中提取，如 N=5 输出 5 道、N=8 输出 8 道），questionNumber 从 1 到 N，不重复。
2. questionType 只允许这四个值：BASIC、PROJECT、BOUNDARY、COMPREHENSIVE，禁止其他值。
3. difficulty 只允许：EASY、MEDIUM、HARD。
4. 题型配比（按 N 四舍五入）：BASIC 30% / PROJECT 40% / BOUNDARY 20% / COMPREHENSIVE 10%，由浅入深排序。
5. 题面 20-50 字，完整清楚，不自问自答。

二、出题内容（最关键）
1. 只围绕【岗位考察要点】中的核心技能与考察重点出题，严禁出现岗位技术栈之外的题目。
2. dimension 必须【逐字原样引用】用户消息中"核心技能"或"考察重点"里的具体名词，不得自创或泛指。
3. content 必须写出具体技术点、工具名或场景，禁止"你掌握的技术"等模糊指代。
4. 简历技能只用于调节难度与侧重，严禁以简历技能作为出题主题。
5. 不同题的 dimension 应尽量覆盖不同的技能，不要每题都用同一个词。

三、输出前强制核对（只输出最终 JSON，不要输出这些步骤）
第1步：从用户消息中摘出"核心技能"和"考察重点"的具体名词，写成清单。
第2步：为每道题分配一个清单内的名词作 dimension，并编写包含具体技术点的 content。
第3步：逐题复核——dimension 是否在清单内？content 是否写了具体技术点？任一不合格就重写该题。

四、输出格式
只输出 JSON，不要输出任何额外文字、解释或代码块标记。
输出一个包含"questions"数组的对象，数组内恰好 N 个元素（N=用户消息指定题量），每元素包含以下字段：
- questionNumber：数字，从 1 到 N（N=用户消息指定的题目数量），不重复
- questionType：BASIC / PROJECT / BOUNDARY / COMPREHENSIVE 四选一
- dimension：核心技能或考察重点的具体名词原文
- difficulty：EASY / MEDIUM / HARD 三选一
- content：20-50 字，包含具体技术点或工具名

反例（绝对禁止，dimension 泛指、content 无具体技术点）：
{"questionNumber":1,"questionType":"BASIC","dimension":"核心技能","difficulty":"EASY","content":"请说明核心技能的关键机制与配置流程。"}{{input_hgtoen-historyChat-历史对话信息}}{{input_hgtoen-currentChatByUser-当前对话信息}}
```

### 2.4 输出 JSON Schema

```json
{
  "questions": [
    {
      "questionNumber": 1,
      "questionType": "BASIC",
      "dimension": "JavaScript基础",
      "difficulty": "EASY",
      "content": "请解释闭包的概念，并举例说明其常见用途与潜在的内存泄漏问题。"
    }
  ]
}
```

### 2.5 边界处理

| 场景 | 处理 |
|------|------|
| resumeInfo 为空 | 按岗位通用要求出题；D 侧 SSE 标 `resumeUsed:false` |
| 岗位信息获取失败 | 工作流内 jobInfo 降级为仅岗位名称；D 侧不阻塞 |
| 输出题目数 ≠ questionCount | D 侧校验，多则截取前 N 道，少则补齐兜底模板题 |
| questionType 配比偏差 | D 侧接受，不强制重试（题型倾向已由 prompt 保证） |

## 三、工作流 2：评分工作流（lingxi-mock-score）

> **职责**：对单道题的候选人作答进行三维评分与点评。

### 3.1 输入参数（拼入 query 文本，工作流 System Prompt 提取）

| 变量名 | 类型 | 必填 | 说明 |
|--------|------|:---:|------|
| `questionContent` | String | 是 | 题目内容（mock_answer.question_content 快照） |
| `questionType` | String | 否 | 题型：BASIC/PROJECT/BOUNDARY/COMPREHENSIVE |
| `referenceAnswer` | String | 否 | 参考要点（D 侧由岗位考察重点拼装，可空） |
| `candidateAnswer` | String | 是 | 候选人作答（跳过时不调用本工作流） |

### 3.2 工作流节点设计

```
[输入节点] 直接接收用户 query 文本（无需自定义参数变量）
      │
      ▼
[大模型节点] 绑定下方 System Prompt，从 query 文本中提取【题目】【题型】【参考要点】【候选人作答】
      │
      ▼
[输出节点] 输出格式 = JSON
      │
      ▼
返回 { "techAccuracyScore", "expressionScore", "knowledgeDepthScore", "aiComment" }
```

### 3.3 System Prompt（平台大模型节点直接粘贴，v2.1 适配 query 文本输入）

> ⚠️ 不要引用输入参数变量（如 `{{...candidateAnswer}}`）——D 侧 `/api/chat` 只传 query 文本，变量为空会导致评分工作流误判"作答字数不足"。

```
你是一个严格的面试评分官，对候选人的单题作答进行评分。

用户输入{{input_hgtoen-currentChatByUser-当前对话信息}}中会包含以下内容（请从用户输入文本中直接提取，不要依赖任何外部变量）：
【题目】题目内容
【题型】BASIC/PROJECT/BOUNDARY/COMPREHENSIVE
【参考要点】参考要点（可能为"无"）
【候选人作答】候选人作答内容

评分维度（各自 0-100 整数）：
1. techAccuracyScore 技术准确度：概念是否正确、有无硬伤、是否给出可行方案
2. expressionScore 表达逻辑：结构是否清晰（分点/总分总/STAR）、是否答非所问
3. knowledgeDepthScore 知识深度：是否涉及原理/源码/底层机制，还是停留在表面

评分要求：
- 【关键】必须基于【候选人作答】的实际内容评分；作答内容充分（超过20字）时不得判定"字数不足"
- 作答少于 20 字 → 各维度分数不超过 50，并在 aiComment 中标注"回答过短"
- 答案存在明显技术错误 → techAccuracyScore 打低分并指出错误
- 【参考要点】为"无"时按通用技术正确性判断，不臆造标准答案
- aiComment：1-2 句话，先肯定亮点再指出不足，具体可操作

输出严格的 JSON，不要输出任何额外文字：
{"techAccuracyScore":82,"expressionScore":75,"knowledgeDepthScore":68,"aiComment":"对原理理解正确，举例得当；但未提及实践细节，深度可再加强。"}
```

输出严格的 JSON，不要输出任何额外文字：
{"techAccuracyScore":82,"expressionScore":75,"knowledgeDepthScore":68,"aiComment":"对闭包原理理解正确，举例得当；但未提及内存泄漏的优化实践，深度可再加强。"}
```

### 3.4 输出 JSON Schema

```json
{
  "techAccuracyScore": 82,
  "expressionScore": 75,
  "knowledgeDepthScore": 68,
  "aiComment": "对闭包原理理解正确，举例得当；但未提及内存泄漏的优化实践，深度可再加强。"
}
```

### 3.5 边界处理

| 场景 | 处理 |
|------|------|
| 作答为空（跳过） | D 侧不调用本工作流，直接写 `is_skipped=1` |
| 评分超时（>15s） | D 侧标记本题未评分（overall=0），不阻塞后续题 |
| 输出分数越界（>100 或 <0） | D 侧 clamp 到 0-100 |
| 分数权重 | D 侧计算：overall = tech×0.5 + expr×0.3 + depth×0.2（系分 5.6.4） |

## 四、工作流 3：报告工作流（lingxi-mock-report）

> **职责**：基于整场面试的题目与评分，生成亮点/短板/提升方案。

### 4.1 输入参数（拼入 query 文本，工作流 System Prompt 提取）

| 变量名 | 类型 | 必填 | 说明 |
|--------|------|:---:|------|
| `jobInfo` | String | 否 | 岗位考察要点（可空，出题时已取） |
| `questions` | String | 是 | 题目+作答摘要+三维分+点评的汇总文本（D 侧拼装，见下） |
| `overallScore` | Number | 是 | 综合均分（D 侧按已评分题计算） |

**D 侧 questions 拼装示例**：
```
题目1(BASIC,78分): 解释闭包。作答摘要: 讲了定义和闭包缓存场景。点评: 概念正确，深度不足。
题目2(PROJECT,85分): 描述一次React性能优化。作答摘要: 提到memo/useMemo和虚拟列表。点评: 方案落地，可再补充profiler验证。
题目3(BOUNDARY,60分): ... 作答摘要: 未答完。点评: 回答过短。
```

### 4.2 工作流节点设计

```
[输入节点] 直接接收用户 query 文本（无需自定义参数变量）
      │
      ▼
[大模型节点] 绑定下方 System Prompt，从 query 文本中提取【岗位考察要点】【答题汇总】【综合得分】
      │
      ▼
[输出节点] 输出格式 = JSON
      │
      ▼
返回 { "highlights", "weaknesses", "improvementPlan" }
```

### 4.3 System Prompt（平台大模型节点直接粘贴，v2.1 适配 query 文本输入）

> ⚠️ 不要引用输入参数变量（如 `{{...questions}}`）——D 侧 `/api/chat` 只传 query 文本，变量为空会导致报告内容空泛。

```
你是一个专业的求职辅导顾问，为候选人复盘一次模拟面试。

用户输入{{input_hgtoen-currentChatByUser-当前对话信息}}中会包含以下内容（请从用户输入文本中直接提取，不要依赖任何外部变量）：
【岗位考察要点】目标岗位考察要点（可能为"无"）
【答题汇总】每道题的题目、作答摘要、三维评分、AI点评
【综合得分】综合均分（0-100）

报告要求：
1. highlights 亮点（2-3 条）：基于高分维度或优秀作答，说明"在哪方面表现好"
2. weaknesses 短板（2-3 条）：基于低分维度或暴露的问题，说明"在哪方面不足"
3. improvementPlan 提升方案（3-5 条）：针对短板给出具体可执行的建议（学习资源/练习方向/答题技巧），
   避免空泛的"多学习""多练习"
4. 某维度均分 >= 80 时，不在对应短板中重复提及
5. 语气客观、具体、有建设性

输出严格的 JSON，不要输出任何额外文字：
{"highlights":["..."],"weaknesses":["..."],"improvementPlan":["..."]}
```

### 4.4 输出 JSON Schema

```json
{
  "highlights": ["React性能优化经验丰富，方案可落地", "对闭包等基础概念掌握扎实"],
  "weaknesses": ["知识深度停留在使用层面，缺乏原理级理解", "能力边界题应变不足，作答超时"],
  "improvementPlan": ["系统学习虚拟DOM与diff算法源码，输出技术笔记", "做5道前端性能优化实战题并限时作答", "学习STAR法则组织面试表达"]
}
```

### 4.5 边界处理

| 场景 | 处理 |
|------|------|
| 无有效答题记录 | D 侧直接返回 40015，不调用本工作流 |
| 只有部分题有评分 | 按实际已评分题聚合，未评分题不纳入均分 |
| 报告生成超时/失败 | D 侧按分数阈值规则生成报告（系分 5.7 降级） |

## 五、通用约定

### 5.1 JSON 输出稳定性

| 手段 | 说明 |
|------|------|
| 平台侧"结构化输出/JSON 模式" | 三个工作流的 LLM 节点**务必开启**（若有此能力），从机制上约束 JSON |
| Prompt 硬约束 | 所有 System Prompt 均要求"输出严格的 JSON，不要任何额外文字" |
| D 侧容错 | 解析失败重试 1 次；仍失败走兜底模板/规则 |

### 5.2 流式响应处理（D 侧 TboxLlmClient）

```java
Iterable<Map<String, Object>> chunks = client.chat(appId, query, userId);
StringBuilder text = new StringBuilder();
for (Map<String, Object> chunk : chunks) {
    // SDK MessageParser 解析后 chunk 结构：{type:"chunk", lane, payload:{text:"...", conversationId, messageId}}
    // 递归提取 payload.text 片段（type=header/meta 无 text，自动跳过）
    text.append(extractText(chunk));
}
return text.toString(); // 完整 JSON
```

> `chat` 默认 stream=true，D 侧拼接 `payload.text` 后整体解析。单次调用整体超时 60s（系分 5.6.2），评分场景 15s。

### 5.3 平台创建步骤（供参考，以百宝箱实际界面为准）

1. 百宝箱开放平台 → 创建应用 → 选择 **工作流** 类型，并**启用「智能体SDK服务」**（开放平台应用配置，未启用会报 `API_AUTH_FAIL 未启用智能体SDK服务`）
2. 大模型节点粘贴对应 System Prompt，**System Prompt 需说明"从用户输入（query 文本）中提取以下字段：jobInfo/resumeInfo/questionCount（或评分/报告对应字段）"**——因为 `/api/chat` 只传文本 query，不传结构化参数
3. 配置**输出**为 JSON（或开启结构化输出）
4. 发布应用，获取 **appId**（三个工作流 appId **已就绪**：见 1.1 表）；授权管理获取 **token**（共用 token **已就绪**：见 1.3）。**⚠️ 关键：发布工作流后，还需在「智能体SDK服务」配置中更新引用到新版本**——只发布工作流不更新 SDK 版本，`/api/chat` 调用仍走旧版（2026-08-04 实测踩坑）；评分/报告工作流改版后同样需要此操作
5. 将 appId/token 填入 D 侧 `application.yml`，`hr.agent.mock` 置 `false`
